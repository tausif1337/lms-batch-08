Chapter 1 · The two questions

Two questions, in this order

The questionIts nameIn this app
Who are you, and can you prove it?Authentication
authn		You type a phone number and a password. The server checks them and hands you a token.
Now that I know who you are, what may you do?Authorisation
authz		Your account has a role — admin, teacher or student — and each role may change different things.

Authentication happens properly once, at login. Authorisation happens on every single request afterwards. A signed-in student and a signed-in admin are equally authenticated; they are not equally authorised.

Chapter 1 · The picture to hold on to

The doorman and the floor plan

At the front desk

A doorman checks your face against your ID card. He is satisfied you are who you say you are, and gives you a plastic badge on a lanyard.

That is authentication. It happens once.

At each door

The badge does not open every door. The server-room reader beeps red at a visitor badge and green at an engineer's. Nobody re-examines your face — the badge speaks for you.

That is authorisation. It happens at every door.

   YOU              FRONT DESK          EACH DOOR
    |                   |                   |
    |--- face + ID ---->|                   |
    |<-- badge ---------|                   |
    |                                       |
    |------------- badge ------------------>|  green
    |------------- badge ------------------>|  red
    |------------- badge ------------------>|  green
Not a simplification

The token login hands you is that badge. The permission classes on each API endpoint are the card readers on each door. This is genuinely how the code is arranged.

Chapter 1 · The fact that makes all of this necessary

The web forgets you instantly

HTTP is stateless

The server keeps no memory between one request and the next. Each request arrives as a complete stranger.

Log in, then a second later ask for the course list — as far as the server is concerned, two unrelated strangers knocked on the door.

The upside: a stateless server can be restarted or duplicated across ten machines and nothing personal is lost, because nothing personal was being held.

So every request that needs to know who you are has to carry the proof with it. Not "log in and be remembered" — log in, get proof, and re-present that proof every single time.

Twenty API calls means twenty presentations of the badge.

Common trap

"I logged in, so why does the server say 401?" Almost always: the request went out without the proof attached. Being logged in is not a state the server holds. It is a piece of data your browser has to send.

Chapter 1 · Two programs, two ports

Why tokens are the natural fit here

        |------------------------->|

  Two separate programs. The frontend is
  NOT pages produced by Django — it is its
  own app that phones the backend for data.

Three consequences you will meet today

  • The frontend must attach the token by hand to every call. Nothing is automatic.
  • Two addresses means the browser's same-origin rule applies — which is why corsheaders is installed. CORS is the server saying "requests from that other address are fine by me".
  • There is no real "log out everywhere" button, because there is no session table to empty.
Chapter 1 · The whole subject, start to finish

Everything today, in nine lines

1. An admin fills in the Accounts form.          ->  POST /api/register/
2. Django hashes the password, saves a User row and a Profile row
   holding the phone number and the role.
3. The new person opens /login and types
   their phone number and password.              ->  POST /api/login/
4. Django finds the Profile by phone, checks the password against
   the stored hash.
5. Django signs two tokens and sends them back, along with the role.
6. The browser stores the access token in localStorage.
7. Every later call attaches it as a header:
       Authorization: Bearer <token>
8. Django verifies the signature, sets request.user, and the
   endpoint's permission class checks the role.
9. Eight hours later the token expires and step 3 happens again.

Every remaining slide today is one of these nine lines, slowed down.

Chapter 2 · Where a person is stored

An account is two rows, in two tables

  auth_user                 backend_profile
  ---------                 ---------------
  id        7               id       4
  username  nadia   <-----  user_id  7
  password  pbkdf2_sha256$  phone    01711110001
  email     nadia@...       role     teacher

Django ships the left one

You did not write User. It arrives with django.contrib.auth. What it does not carry: a phone number, and a role. Django has no opinion about either.

backend/backend/serializers.py 
from django.contrib.auth import get_user_model

User = get_user_model()

get_user_model() asks Django "whichever model is in charge of accounts, give me that one". If the project ever swapped in a custom user model, this line keeps working while from django.contrib.auth.models import User would quietly point at the wrong table.

The surprise

You log in with the phone number — not the username, not the email. That is why the phone lives on Profile, and why the login view searches there first.

Chapter 2 · models.py

The second table, in full

backend/backend/models.py 
class Profile(models.Model):
    ADMIN   = "admin"
    TEACHER = "teacher"
    STUDENT = "student"

    ROLE_CHOICES = [
        (ADMIN,   "Admin"),
        (TEACHER, "Teacher"),
        (STUDENT, "Student"),
    ]

    user  = models.OneToOneField(User, on_delete=models.CASCADE)
    phone = models.CharField(max_length=20, unique=True)
    role  = models.CharField(max_length=10, choices=ROLE_CHOICES,
                             default=STUDENT)

unique=True does real work

The login view runs Profile.objects.get(phone=phone) — get, singular. If two accounts shared a number, that call raises MultipleObjectsReturned and nobody could sign in. The uniqueness rule is load-bearing, not tidiness.

default=STUDENT is a policy

An account with nothing specified is the least powerful kind. Defaults should fail towards less access, never more.

on_delete=CASCADE

Delete the User and the Profile goes with it. A phone number and role belonging to a deleted account are meaningless leftovers.

Chapter 2 · Day-one trap

Your brand new superuser cannot log in

Why

createsuperuser belongs to Django. It knows nothing about your Profile model, so it creates the User row alone. No phone number — and the login screen asks for a phone number.

Nothing is broken. The row it needs simply is not there yet. Fix it once, by hand, in the Django admin: Profiles → Add profile → pick your user, type a phone, choose role Admin.

python manage.py createsuperuser
python manage.py runserver 8001
# then http://127.0.0.1:8001/admin/
backend/backend/permissions.py — the code plans for this 
def role_of(user):
    if not user or not user.is_authenticated:
        return None

    if user.is_superuser:
        return Profile.ADMIN

    profile = (Profile.objects.filter(user=user)
                             .only("role").first())
    if profile is None:
        return Profile.STUDENT

    return profile.role

Read the last branch as a policy, not a fallback: when the code is unsure who you are, it gives you less, not more.

Chapter 3 · A deliberate design decision

A student does not make their own account

An admin makes it for them and picks the role at the same time. There is no sign-up link on the login screen.

frontend/src/App.jsx 
{/* /register used to be a public page. There is no
    public sign-up any more: an admin creates accounts
    at /accounts, inside the app. */}
<Route path="/register"
       element={<Navigate to="/login" replace />} />

Why

Because of what a role is worth. In a school system, the difference between a student account and a teacher account is the difference between reading grades and setting them.

If anybody could sign up, then either everyone starts as a student and an admin promotes them one by one anyway — or the role is self-declared, which is no protection at all.

The trade-off, and it is real

Somebody has to be an admin before anybody can be anything. That is the chicken-and-egg problem we just solved with createsuperuser plus a hand-made Profile.

Chapter 3 · The word, defined properly

A serializer is a translator that works both ways

   JSON over the web        Rows in the database
   {"phone": "0171...",     backend_profile
    "role": "teacher"}      user_id | phone | role
          |                        ^
          |    COMING IN           |
          +------ validate --------+
          |    check every field is present,
          |    the right type, acceptable
          |
          +------ GOING OUT -------+
                 choose which fields the
                 outside world may see

Coming in

Take the JSON the browser sent, check it, then create or update rows. This is where validation lives.

Going out

Take rows and turn them into JSON, choosing which fields are allowed to be seen.

That second half matters as much as the first. The password column is never in the outgoing JSON — and that is a decision written down in the serializer, not something that happens by luck.

Chapter 3 · Field by field

The four fields written out by hand

backend/backend/serializers.py 
class RegisterSerializer(serializers.ModelSerializer):
    phone      = serializers.CharField(required=True,
                                       write_only=True)
    first_name = serializers.CharField(required=True)
    email      = serializers.EmailField(required=True)
    role = serializers.ChoiceField(
        choices=Profile.ROLE_CHOICES,
        required=False,
        default=Profile.STUDENT,
    )

    class Meta:
        model  = User
        fields = ['id','username','email','password',
                  'phone','first_name','last_name','role']
        read_only_fields = ['id']
        extra_kwargs = {'password': {'write_only': True}}

ModelSerializer means "look at the model in Meta and work out most of the fields yourself". Because model = User, five fields come free with the right types and lengths.

FieldWhy it is written out
phoneNot a User column at all — it belongs to Profile. Declaring it here lets it arrive in the same request.
first_nameDjango's version allows blank. This app insists on one.
emailNeeded later by the password reset flow, so it cannot be optional.
roleAlso a Profile column. ChoiceField restricts it to three known values — anything else is rejected before any row is written.

Chapter 3 · A DRF naming convention

Turning crashes into sentences

backend/backend/serializers.py 
def validate_phone(self, value):
    if Profile.objects.filter(phone=value).exists():
        raise serializers.ValidationError(
            "This phone number is already registered.")
    return value

def validate_username(self, value):
    if User.objects.filter(username=value).exists():
        raise serializers.ValidationError(
            "That username is already taken.")
    return value

def validate_password(self, value):
    validate_password(value)   # Django's own rules
    return value

Define a method called validate_<fieldname> and DRF calls it automatically with that field's value. Return the value to accept it; raise ValidationError to reject it with a message.

Why bother — the database already enforces this

Both columns are already unique, so the database would refuse anyway. Doing it here turns a 500 crash into a 400 with a sentence a human can act on.

The database protects the data. The serializer protects the person using the form.

{"phone":    ["This phone number is already registered."],
 "password": ["This password is too common."]}

Every message is a list — one field can fail more than one rule at once.

Chapter 3 · Two rows have to appear

All of it, or none of it

backend/backend/serializers.py 
@transaction.atomic
def create(self, validated_data):
    phone      = validated_data.pop('phone')
    email      = validated_data.pop('email')
    role       = validated_data.pop('role', Profile.STUDENT)
    first_name = validated_data.pop('first_name', '')
    last_name  = validated_data.pop('last_name', '')

    user = User.objects.create_user(
        username   = validated_data['username'],
        email      = email,
        password   = validated_data['password'],
        first_name = first_name,
        last_name  = last_name,
    )
    Profile.objects.create(user=user, phone=phone, role=role)
    return user

Read the decorator first

@transaction.atomic wraps everything inside in a database transaction: either all of it is saved or none of it is.

Without it

A failure halfway through leaves a User with no Profile: an account with a password and no way to log in — and a username now taken, so the admin cannot even retry with the same name.

Atomic makes the pair of rows an all-or-nothing unit, which is exactly what they are.

Chapter 4 · The rule with no exceptions

A password is never stored

Not encrypted. Not encoded. Not hidden in a column nobody looks at. Never stored at all.

The reason is not your database

It is that people reuse passwords. The account in your teaching LMS very probably shares a password with somebody's email — and their email is the master key to everything else they own.

Storing it readably makes you the weak link in somebody else's whole life. That is why the rule has no exceptions, even for a project nobody will deploy.

So how can the server check a password it does not have?

By storing something derived from it that cannot be turned back.

  login attempt      stored in the database
      |                      |
   "opensesame"        pbkdf2_sha256$...$tPM4Dck...
      |                      |
      +---- hash it ----+    |
                        v    v
                      are they equal?

  At no point did the server know either password.
Chapter 4 · One-way calculation

Three properties, plus one that surprises people

1 · Deterministic

The same input always gives the same output. That is what makes checking possible at all.

2 · One-way

Given the output there is no calculation that recovers the input. The only attack is guessing, hashing, comparing.

3 · Avalanche

A tiny change to the input changes the output completely. No partial credit, no "warm" hashes.

4 · For passwords only — it must be slow on purpose

A fast hash lets an attacker who steals the database try billions of guesses a second. A password hash is deliberately built to take a noticeable fraction of a second: nothing when you log in once, ruinous when you are running a dictionary.

Django 5.2 default: PBKDF2-SHA256 at 1,000,000 iterations.

Chapter 4 · A real row, dissected

Four parts, cut by $

pbkdf2_sha256$1000000$z5Chg0kZql1bmLAAHi3Ws7$tPM4DckZXkyDDVZmZHe4uV7lyF/509Ox6GKw+i9ZlxY=
└─ algorithm ─┘└ iters ┘└────── salt ───────┘└─────────────── hash ───────────────────┘
PartMeaning
algorithmWhich hash function was used. Django 5.2's default.
iterationsRun a million times over. This is the deliberate slowness.
saltRandom text generated when the password was set.
hashThe actual result.
Why store the settings too

Each row remembers how it was made. That is what lets Django raise the iteration count in a future version without breaking anybody — when you next log in, Django notices your row is below the current standard and quietly re-hashes at the new setting.

Chapter 4 · Same word, twice

The salt, and why it is not a secret

pbkdf2_sha256$1000000$z5Chg0kZql1bmLAAHi3Ws7$tPM4DckZXkyDDVZmZHe4uV7lyF/509Ox6GKw+i9ZlxY=
pbkdf2_sha256$1000000$gP9O5ZrDz5bM00XoM0RukX$pzjvPhl9jFYCKhBCjD6Ya5doVL9W1o2xjO18WJ5LQpg=

Same password. Completely different stored strings, because each got a fresh random salt mixed in before hashing. Same input and same salt still gives the same output — which is why the salt has to be stored in plain sight. It is not a secret. It has a different job.

Job 1 · Identical passwords stop looking identical

Without salt, everyone who chose 123456 would have the same row, and one glance down the column tells an attacker which accounts to try first.

Job 2 · Precomputed tables become useless

Attackers keep enormous lists of common passwords already hashed. Those lists are worthless against a salt they have never seen — every password must now be attacked separately.

Chapter 4 · Not laziness

One message for two different failures

try:
    profile = Profile.objects.get(phone=phone)
    user = profile.user
except Profile.DoesNotExist:
    return Response({'error': 'Invalid phone or password'},
                    status=400)

if not user.check_password(password):
    return Response({'error': 'Invalid phone or password'},
                    status=400)

The view really does have two separate failure paths — no Profile with that phone number, and a Profile whose password did not match — and it deliberately answers both with the same sentence and the same status code.

Account enumeration

If the messages differed — "no such phone number" vs "wrong password" — anyone could feed the endpoint a list of phone numbers and learn which ones have accounts, without guessing a single password.

That turns a login form into a directory of your users. One vague message closes it.

The same reasoning appears again in the forgotten-password flow, later today.

Chapter 5 · views.py, in full

Thirty lines, and you have seen most of them

class LoginView(APIView):
    permission_classes = [AllowAny]

    def post(self, request):
        serializer = LoginSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        phone    = serializer.validated_data['phone']
        password = serializer.validated_data['password']

        try:
            profile = Profile.objects.get(phone=phone)
            user = profile.user
        except Profile.DoesNotExist:
            return Response({'error': 'Invalid phone or password'},
                            status=400)

        if not user.check_password(password):
            return Response({'error': 'Invalid phone or password'},
                            status=400)

        tokens = get_tokens_for_user(user)
        return Response({
            'message':  'Login successful',
            'user_id':  user.id,
            'username': user.username,
            'role':     role_of(user),
            'tokens':   tokens,
        })
StepWhat it does
1 · shapeis_valid(raise_exception=True) — "check it, and if it is wrong, stop here and answer 400 with the reasons". No if needed; the exception ends the method.
2 · lookupThe search starts in Profile, not User. Then profile.user follows the one-to-one link.
3 · passwordOne line. Everything below it is the exact moment authentication succeeds.
4 · tokensRefreshToken.for_user(user) signs two strings. Nothing is written to any table.
One habit

Read from validated_data, never request.data — that keeps unchecked input out of your logic.

Where everyone loses ten minutes

Most JWT tutorials answer with access at the top level, so most copied code reads data.access and gets undefined. Here it is data.tokens.access.

The role is included

Not because the frontend is trusted with it — so the sidebar can hide links a student cannot use. The server checks the role again on every request regardless.

Nothing was written to any table

At the end of a successful login this app has not recorded that you logged in. The proof went out the door with you.

The refresh token is sent, then dropped

This backend has no refresh endpoint. The frontend stores only the access token. We come back to what that costs.

Chapter 6 · What a JWT is

A signed note, not a claim ticket

The session approach gives you a numbered claim ticket and keeps a ledger at the desk.

The token approach gives you a note that reads "the bearer of this note is employee 7, valid until 6pm", signed by the manager — and keeps no ledger at all.

  • Anyone can read the note.
  • Nobody can alter it, because the signature would stop matching.
  • Anyone holding it is treated as employee 7 — which is why the word in the HTTP header is literally Bearer.

What is actually inside

ClaimWhat it does here
token_typeStops a refresh token being used where an access token is expected

Note what is NOT in there

Chapter 6 · This catches out experienced developers

Not encrypted. Signed.

A JWT is readable by anybody who has it

Encoding is not encryption. If you put a person's email, salary or role in a token, everyone holding that token can read it — including the person themselves, and anyone who steals it.

What the signature guarantees is integrity

Not secrecy. Nobody can change the contents. Edit "user_id": 7 to "user_id": 1, re-encode, and the signature no longer matches. The server rejects it, because only someone holding the secret key can produce a valid signature.

So the rule for a payload is simple: facts you would not mind the holder reading, and nothing you would mind them knowing.

backend/lms/settings.py 
SECRET_KEY = 'django-insecure-@hg+%+(*w2m0jh=8$ksn...'

Everything rests on that string. Anybody who knows it can sign a token claiming to be user_id: 1, and your server will believe it completely — because believing signatures is the entire mechanism.

Do not ship this

A SECRET_KEY committed to Git is a real, exploitable vulnerability, not a style issue. On a real deployment it must be read from an environment variable and never appear in the repository.

Changing it invalidates every token at once — worth knowing both as a consequence and as a blunt emergency tool.

Chapter 6 · The eight-hour decision

A trade, written down honestly

SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME":  timedelta(hours=8),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=7),
    "AUTH_HEADER_TYPES": ("Bearer",),
}

The library default is 5 minutes

Without a refresh endpoint, five minutes throws you back to the login screen in the middle of typing a lesson description. So the author widened the access token to eight hours instead of building the refresh flow.

What it costs: a stolen token is useful for up to eight hours instead of five minutes.
What it buys: an app usable for a day's work, and one less endpoint to build.

The habit worth taking

When you loosen a security setting, write down what you traded and why, the way that settings file does.

AUTH_HEADER_TYPES is the third line and the one you meet in practice: write Token <t> or JWT <t> and this server treats you as a stranger.

Chapter 6 · The cost of the whole approach

You cannot un-sign a signed note

The server keeps no list of valid tokens, so there is nothing to delete. Once an access token is out there, it works until exp passes, and nothing short of changing SECRET_KEY can stop it.

Compare with sessions, where logging somebody out is one DELETE.

Three places this project runs into it — each handled honestly

Logging out

The frontend deletes its copy. The token itself stays valid until it expires. There is no logout endpoint, because there is nothing useful for one to do.

Changing your password

Refresh tokens are blacklisted; the access token cannot be. So the app signs you out on the spot and makes you log back in.

Demoting someone

This one is fine, by design. The role is not in the token, so the change applies to the very next request.

const TOKEN_KEY = "lms_access_token";
const USER_KEY  = "lms_user";

export function getToken() {
  return localStorage.getItem(TOKEN_KEY);
}

export function saveSession(token, user) {
  localStorage.setItem(TOKEN_KEY, token);
  localStorage.setItem(USER_KEY, JSON.stringify(user));
}

export function clearSession() {
  localStorage.removeItem(TOKEN_KEY);
  localStorage.removeItem(USER_KEY);
}

The token has to survive you pressing F5. A JavaScript variable does not. localStorage is a small store of text the browser keeps per website, permanently, until code or the user clears it.

Chapter 7 · The heart of api.js

How does the server know it is me?

async function request(path, options = {}) {
  const { auth = true, ...rest } = options;

  const headers = { ...(rest.headers ?? {}) };
  if (rest.body !== undefined) {
    headers["Content-Type"] = "application/json";
  }

  const token = getToken();
  if (auth && token) {
    headers.Authorization = `Bearer ${token}`;
  }

  let response;
  try {
    response = await fetch(BASE_URL + path, { ...rest, headers });
  } catch {
    throw new Error("Could not reach the server...");
  }
  ...

Every call in the app goes through this one function — which is exactly why it can guarantee the header is there.

  • auth = true is the default. Only three calls opt out: login, and the two halves of password reset. Defaulting to secure and opting out deliberately is the same instinct as DEFAULT_PERMISSION_CLASSES on the server.
  • The header is spelled Authorization: Bearer <token>. Note the space and the capital B.
  • The catch fires when the request never reached a server at all — Django down, wrong port, no network. That is different from a request that arrives and is refused.

Chapter 7 · What React context is for

Surviving a page refresh

frontend/src/AuthContext.jsx 
export function AuthProvider({ children }) {
  // The token is read back out of localStorage on the
  // first render so a page refresh does not log you out.
  const [user, setUser] =
      useState(() => getSavedUser());
  const [isLoggedIn, setIsLoggedIn] =
      useState(() => Boolean(getToken()));
async function logIn(phone, password) {
  const data = await loginRequest(phone, password);

  // The tokens are nested. data.access does not exist.
  const nextUser = { id: data.user_id,
                     username: data.username,
                     role: data.role };
  saveSession(data.tokens.access, nextUser);

  setUser(nextUser);
  setIsLoggedIn(true);
}

Both useState calls take a function, not a value. React calls it once, on the very first render — so the app boots by asking localStorage "was somebody signed in here?" and starts in the right state with no flicker through a logged-out screen.

Why both localStorage and React state

localStorage survives a reload but React does not watch it. React state redraws the screen but vanishes on reload.

Write one without the other and you get the two classic bugs: an app that still looks signed out until you refresh, or one that looks signed in until you refresh.

Chapter 7 · The most important sentence today

ProtectedRoute is a convenience, not a security control

// `role`, when given, is the one role allowed through.
// Hiding a link in the sidebar is not enough on its own
// — somebody can always type the URL.
export default function ProtectedRoute({ role, children }) {
  const { isLoggedIn, user } = useAuth();
  const location = useLocation();

  if (!isLoggedIn) {
    return <Navigate to="/login" replace
             state={{ from: location.pathname }} />;
  }

  // The role arrives a moment after the token when a saved
  // session is being topped up from /profile/.
  if (role && !user?.role) return null;

  if (role && user.role !== role)
    return <Navigate to="/" replace />;

  return children;
}

Three checks, in order. Not signed in → /login, with a note of where you were going, which is the goBackTo the login form used. Role required but not known yet → draw nothing for a moment rather than guess wrong. Wrong role → back to the dashboard.

Read this carefully

It runs in the browser, on code the visitor could edit. It exists so people are not shown doors that will not open for them.

The thing that actually stops a student creating accounts is IsAdmin on the server.

Chapter 8 · Authentication hands over to authorisation

How a header becomes a person

backend/lms/settings.py 
REST_FRAMEWORK = {

    "rest_framework_simplejwt.authentication"
    ".JWTAuthentication",
  ),

You never wrote code to read the Authorization header. One setting arranged it.

The price of not putting the role in the token

Step 5 is a database read on every request. In exchange, a change made in the Django admin takes effect on the very next call rather than in eight hours.

Before any view runs, in order

  • Look for an Authorization header. Nothing there? Stop — the caller is anonymous.
  • Check it starts with Bearer. Take the rest as the token.
  • Verify the signature with SECRET_KEY. Altered in any way? Reject.
  • Check exp against the clock. Expired? Reject.
  • Read user_id out of the payload, load that row from auth_user, and put it on the request.

After which every view can simply write request.user. When nobody is signed in it is Django's AnonymousUser, whose is_authenticated is False — which is why the permission code checks that flag rather than testing for None.

Chapter 8 · The card readers on each door

Four classes, one shared base

class RoleWritePermission(BasePermission):
    """Signed-in accounts read. Only these roles write."""
    roles_that_may_write = ()
    message = "Your role does not allow this change."

    def has_permission(self, request, view):
        if not request.user or \
           not request.user.is_authenticated:
            return False

        if request.method in SAFE_METHODS:
            return True

        return role_of(request.user) in \
               self.roles_that_may_write

A permission class is an object with a has_permission() method returning True or False. DRF calls it before the view runs. That is the entire interface.

SAFE_METHODS is DRF's tuple ("GET","HEAD","OPTIONS") — the methods that only look. Anything else changes something and falls through to the role check.

Each carries its own message, which is why refusals in this app read like sentences rather than "Permission denied".

Chapter 8 · The most interesting docstring in the codebase

A student may hand work in — and nothing else

    A student cannot edit or delete a submission, because

    server has no way to tell whose work it is.

        if (request.method == "POST"
                and request.user
                and request.user.is_authenticated
                and role_of(request.user) == Profile.STUDENT):

A logged-in student is a User. A submission belongs to a Student. The server cannot tell whether the person POSTing a submission is the student named in it — so it allows the create and forbids everything else.

The general shape of a whole class of security bugs

The permission check can only be as precise as the data model allows. No cleverness in permissions.py can answer "is this your submission?" while the answer is not recorded anywhere.

Chapter 9 · Knowing the old one is what makes it yours to change

A live session is not enough

def validate_current_password(self, value):
    # Knowing the old password is what makes this yours to
    # change. Without it, a borrowed browser tab would be
    # enough to take the account.
    if not self.context["request"].user.check_password(value):
        raise serializers.ValidationError(
            "That is not your current password.")
    return value

def validate(self, attrs):
    if attrs["new_password"] != attrs["confirm_password"]:
        raise ...("The two new passwords do not match.")
    if attrs["new_password"] == attrs["current_password"]:
        raise ...("The new password has to be different.")
    validate_password(attrs["new_password"],
                      user=self.context["request"].user)
    return attrs

Two kinds of validation method. validate_<field> checks one field on its own. Plain validate runs afterwards and can see all the fields at once — the only way to compare two of them.

Why ask for the current password at all?

If a live session were enough, walking away from an unlocked laptop would mean losing the account permanently rather than temporarily — the person at your desk could lock you out of your own login.

Asking for the current password means the attacker needs the secret, not just the chair.

The view operates on request.user and nothing else, so there is no field anywhere that could aim it at another account. And set_password is followed immediately by save().

Chapter 9 · Single-use, without storing a thing

uid answers "who". token proves it.

uid   = urlsafe_base64_encode(force_bytes(user.pk))
token = default_token_generator.make_token(user)

reset_link = f"{FRONTEND_PASSWORD_RESET_URL}" \
             f"?uid={uid}&token={token}"

uid is the primary key, base64url-encoded so it survives a URL. User 7 becomes Nw. Nothing secret about it — encoding, again, is not encryption.

token is not a JWT. Django builds a hash out of four ingredients, signed with SECRET_KEY:

  • the user's primary key
  • the current password hash
  • the account's last_login timestamp
  • the time the token was made
PropertyWhy it holds
Single useThe password hash is an ingredient. Once the password changes, the hash changes and the token no longer verifies.
ExpiresThe creation time is an ingredient, checked against PASSWORD_RESET_TIMEOUT — 1 hour here, vs Django's default of 3 days.
UnforgeableSigned with SECRET_KEY, which the requester does not have.

The elegant bit

Nobody wrote code to mark the token as used. It invalidates itself as a side effect of the thing it was for.

And the same trick as login

The endpoint answers "If an account exists with this email, a reset link has been sent." — whether or not it does. Anti-enumeration, one more time.

Chapter 12 · The honest list

A teaching app, not a bank

Three settings that must move to the environment

SECRET_KEY in the file is complete authentication bypass for anyone who reads the repo. DEBUG = True returns a full traceback — file paths, local variables, settings — to any caller. And a real email address sits as a default next to EMAIL_HOST_PASSWORD.

No rate limit on login

Nothing counts failed attempts, nothing locks an account, no CAPTCHA. This is the most likely way this app would actually be broken into — and the cheapest to fix:

"DEFAULT_THROTTLE_CLASSES":
    ("rest_framework.throttling.AnonRateThrottle",),
"DEFAULT_THROTTLE_RATES": {"anon": "20/hour"},

The token in localStorage

Any JavaScript on the page can read it — including anything injected through an XSS hole. The alternative, an HttpOnly cookie, closes this and opens CSRF instead. Neither choice is free; the difference is which attack you are prepared for.

Also missing

Email verification. Two-factor. An audit trail of who changed a role. Account lockout or notification. A logout endpoint.

Read that list as a curriculum, not a complaint

Each item is a real system's real feature — and now you know exactly which problem each one exists to solve.

Recap · If you remember nothing else

The eight sentences worth keeping

  • HTTP forgets you between requests, so proof travels with every one.
  • You log in with the phone number, because that is what the Profile is found by.
  • Passwords are hashed, never stored; the salt makes identical passwords look different.
  • A JWT is signed, not encrypted — anyone holding it can read it.
  • The role is not in the token, so a change in the admin applies to the next request.
  • 401 means "I do not know you". 403 means "I know you, and no".
  • The frontend's permission rules hide buttons; the server's rules are what stop anything.
  • A signed note cannot be taken back, which is why logging out only deletes your copy.

The five-minute checklist, when something breaks

  • Is Django running, on the port the frontend calls?
  • What is the status code? Network tab, or -i in curl.

  • Is there a token in localStorage, and is it whole? Check exp.
  • Does the account have a Profile, with the role you expect?
  • Anything in the runserver terminal?
